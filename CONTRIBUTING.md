# Contributing to Awesome Loop Models

Thank you for contributing.

This repository curates:
- papers on loop models — architectures where a shared learned internal layer, block, module, or operator is reused, within a single forward pass or by feeding a computed state back through the same layers for the next token or step
- selected long-form technical blogs about loop models

---

## Preferred Workflow: Use the Submission Guide First

Please start from the submission guide page:

- submit.html

The guide is the intended staging page before opening a pull request:
- it lets you choose Paper vs Blog explicitly
- it lets you fill the main submission fields once on the guide page
- it offers controlled pickers for taxonomy sections and design axes before you leave for GitHub
- it generates the target YAML path and the generated YAML content
- it tells you exactly what path and YAML to copy into your own fork

GitHub cannot auto-create a fork with the generated YAML already inserted on your behalf from a public link. After reviewing the generated file on the guide page:

1. Fork the repo to your own GitHub account.
2. Create a branch in your fork.
3. Create the generated file path in that branch and paste the generated YAML.
4. Open a pull request back to this repo.

If you already have a fork, skip straight to the branch / file / PR steps. The repository PR template will appear on the final PR page.

Do not edit `README.md`, `papers.json`, `catalog/papers-*.json`, `briefing-latest.json`, `submission-meta.json`, or `TAGS.md` by hand. They are generated by `scripts/build.py`.

Before submitting paper metadata, run the read-only catalog audit from the
repository root:

```bash
python3 scripts/audit_catalog.py
python3 scripts/audit_catalog.py --format json
python3 -m unittest tests.test_audit_catalog
```

Errors are blocking structural, identity, URL, or controlled-vocabulary problems;
warnings require human review but do not make the command fail. The auditor
never edits YAML and does not replace primary-source review of paper scope,
descriptions, or taxonomy-section and design-axis accuracy. See
[`audits/README.md`](audits/README.md) for the full contract.

## Quick Scope Check

### Papers

The strict paper catalog targets work where:

> A shared learned internal layer, block, module, or operator is reused, either along depth within one forward pass or along time, by feeding a state it computed back through the same layers for the next token or step.

Good fits:
- recurrent-depth / looped transformers
- adaptive halting over repeated block application
- deep equilibrium / fixed-point / implicit-layer models
- shared processors repeatedly executed for algorithmic reasoning
- depth folded into time: Feedback Transformers, Latent Recurrent Transformers, shift-1 and pipelined loops that feed a high-level state back through the same layers for the next token

Usually out of scope:
- agent loops
- plain autoregressive decoding
- latent reasoning via repeated full forward calls
- diffusion / energy-based reasoning
- recursive model calls
- untied depth scaling
- external search or planning over arbitrary layer orders when the qualifying loop is not a shared internal forward-process recurrence

Recurrence over time counts when it reuses the model's layers on a state they already computed. Ordinary sequence recurrence (RNN, LSTM, state-space or linear-attention updates that only carry a memory across steps) is not enough by itself, and neither is COCONUT-style latent chain-of-thought that only feeds the last hidden state back as the next input.

Rare curator-approved exceptions may use `catalog_fit: adjacent`. These entries stay visible for conceptual value, and are explicitly labeled outside strict scope. Omit `catalog_fit` for normal strict-scope submissions.

### What counts as a blog?

A blog belongs here only if it is a substantive public long-form technical post about loop models or closely related loop-model questions.

Good fits:
- technical deep-dives
- lab blog posts
- long-form essays
- tutorials with real technical content
- X articles / Substack posts / personal blog posts with substantial analysis

Usually out of scope:
- short tweets or short announcement posts
- marketing pages
- bare link roundups with no real analysis
- generic news reposts
- project pages that do not contain meaningful technical writing

Blogs list the taxonomy sections they discuss but do not use the paper design axes. They live in one flat `Blogs` section.

If a paper or blog is borderline, explain the fit clearly in the pull request description. Contributors should not set `catalog_fit: adjacent` without maintainer agreement.

See [TAXONOMY.md](TAXONOMY.md) for the full paper taxonomy and the blog-section rule.

## Taxonomy: the topic map

Papers are classified by the chapters and sections of the repo's topic map. See [TAXONOMY.md](TAXONOMY.md) for the full vocabulary and how to choose values, and [TAGS.md](TAGS.md) for current usage counts.

- `survey_section` (historical field name): the taxonomy sections the paper belongs to, **primary first**. The browser files the paper under its primary section.
- `loop_topology`, `sharing` and `depth_control` describe the loop (§4), one value each.
- `claims` lists what the paper argues looping buys or costs; `comparison` records the control in any looped-vs-untied comparison (`[]` if none).
- `survey_core: true` (historical field name) marks core reference papers for loop models; maintainers set it.

All values are controlled and the build validates them; adding a value is a taxonomy change. **There are no free-form tags.** Model, method and dataset names go in the title and `desc`. The build rejects the retired fields `category`, `category_path`, `subcategory`, `foundation`, `mechanism_tags`, `focus_tags`, `domain_tags` and `tags`. If no section fits, stop and propose a controlled taxonomy-vocabulary change to the maintainer instead of forcing a match.

## Metadata Reference

If you want to help maintainers by drafting metadata before opening GitHub's editor, use one of the following schemas.

### Paper YAML sketch

```yaml
title: "Paper Title"
authors:
  - "First Author"
  - "Second Author"
year: 2026
published_date: "2026-04-20"
added_date: "2026-04-20"
venue: "arXiv"
survey_section:
  - "architecture/depth-control"
  - "scaling/test-time"
loop_topology: "prelude-core-coda"
sharing: "full"
depth_control: "sampled-train"
claims:
  - "test-time-scaling"
comparison: []
survey_core: false
desc: "One concise sentence describing the paper's core contribution."
links:
  arxiv: "https://arxiv.org/abs/XXXX.XXXXX"
  paper: ""
  github: "https://github.com/..."
  hf: ""
  openreview: ""
  project: ""
  comment:
    - label: "Deep-dive thread"
      url: "https://x.com/..."
  twitter: ""
```

For a maintainer-approved adjacent exception, add `catalog_fit: "adjacent"`.

### Blog YAML sketch

```yaml
title: "Blog Title"
authors:
  - "Author Name"
year: 2026
published_date: "2026-04-21"
added_date: "2026-04-21"
venue: "X Article"
survey_section:
  - "architecture/topology"
desc: "One concise sentence describing the post's technical value."
links:
  blog: "https://x.com/..."
  github: ""
  project: ""
  twitter: ""
  comment:
    - label: "Follow-up discussion"
      url: "https://x.com/..."
```

Notes for papers:
- pick the primary `survey_section` by the paper's main contribution, following [TAXONOMY.md](TAXONOMY.md)
- for published papers, `year` is the conference/workshop edition or journal publication year shown in venue labels (for example, `ICML 2026`). Keep `published_date` as the first public release date, even when it is an earlier year. arXiv labels remain `arXiv`, and venue names already containing a year do not repeat it.
- use `venue: arXiv` when no publication venue is known. Set `peer_reviewed: true` only with an official conference, workshop, or journal acceptance/publication record, and save its HTTPS URL in `venue_source`. Submission pages alone are not acceptance evidence; a reviewed non-archival workshop still counts.
- `python3 scripts/fetch_publication.py` previews verified venue updates; add `--write` to save them or `--only <paper-id>` to limit the check. The daily metrics workflow also refreshes these fields. Failed or inconclusive lookups preserve curated metadata; a missing flag means unverified, not rejected.
- The website's **Peer-reviewed** filter respects an explicit boolean status when present; otherwise it uses the catalog's curated conference, workshop, or journal venue. Missing crawler evidence does not erase an existing publication record. arXiv, unknown, and submission-only records are excluded. The **High influence** badge and filter share one independent rule: citations must strictly exceed completed months since `published_date`, using UTC dates and month-end-clamped anniversaries. A paper less than one month old has zero completed months, so one citation qualifies. It can be combined with Peer-reviewed and other filters; Blogs are unaffected. It is a citation-age heuristic, not a quality assessment. Never reset `published_date` when a preprint is accepted.

Notes for blogs:
- blogs carry `survey_section` only; they do not use the design axes, `claims`, `comparison` or `survey_core`
- `links.blog` is the canonical primary URL for a blog entry
- use `venue` to describe the source, for example `X Article`, `Lab Blog`, `Substack`, or `Personal Blog`

Notes for both papers and blogs:
- `published_date` is required for all papers and blogs; use the original release date and keep it as a quoted `YYYY-MM-DD` string
- `added_date` is required for new paper entries and optional for blogs; it is the repo intake date used by the daily feed, and the greatest valid paper value defines the `Newly Arrived` batch while blogs are excluded; keep it as a quoted `YYYY-MM-DD` string

### Filename Rules

Use the generated path from `submit.html` instead of inventing a new filename by hand.

- Papers should use `papers/<arxiv_id>.yaml` when the primary link is an arXiv URL.
- Papers without an arXiv ID should use `papers/<shortname>.yaml`, where `shortname` is a stable kebab-case slug.
- Blogs should use `blogs/YYYY-MM-DD-shortname.yaml`.
- For blogs, `YYYY-MM-DD` must match the blog's `published_date`.
- For blogs, `shortname` can be provided manually; if omitted, the submission guide will derive it from the title.
- Blog filenames must not collide with an existing file in `blogs/`.

### Browser filters

The interactive browser groups papers by Part → Chapter → Section (primary section) and filters by section and the design axes (`loop_topology`, `sharing`, `depth_control`, `claims`, `comparison`). Search covers titles, authors and descriptions.

## Static Site Asset Budgets

After regenerating the canonical site artifacts, run the deterministic, offline budget check:

```bash
python3 scripts/build.py
python3 scripts/check_asset_budgets.py
```

The checker reports every measured value alongside its limit and lists all violations in one run. Current budgets are:

| Asset or schema contract | Limit |
|---|---:|
| `papers.json` manifest deterministic gzip size (`mtime=0`) | 60,000 bytes |
| Each `catalog/papers-NNN.json` chunk, deterministic gzip size | 60,000 bytes |
| Papers per chunk | At most 100 |
| `papers.json.briefings` | At most 1 item |
| `content` keys anywhere within browser briefings | 0 |
| `briefing-latest.json` deterministic gzip size | 60,000 bytes |
| `submission-meta.json` raw size | 20,000 bytes |
| `assets/favicon.png` raw size | 10,000 bytes |

Missing files, malformed JSON, and invalid generated JSON schemas also fail the check. On every pull request, CI regenerates the offline artifacts, checks these budgets, and runs the unit tests. Citation metrics fetching and generated-file commits remain disabled for pull requests, so the PR gate performs no metrics network access and does not write back to the branch. Do not evaluate the checker against stale generated files locally.

GitHub Pages transfers these files compressed, so deterministic gzip size is the network budget; a separate raw-byte cap would only limit harmless formatting and repetition. `papers.json` is a small manifest: it holds catalog metadata, blogs, the latest briefing, and a `paper_chunks` list. Paper records live in `catalog/papers-NNN.json`, 100 papers per chunk in catalog order. Each manifest row records the chunk's path, paper count, and a 12-character SHA-256 `version`, which `index.html` appends as a cache-busting query and the checker verifies. The newest briefing's full Markdown body lives only in `briefing-latest.json` (date, title, status, summary, highlights, candidates, source path and `body_markdown`), which the browser's **Briefing** tab fetches on first open; `papers.json.meta.latest_briefing_version` is its cache-busting hash. The checker requires every field, matches its date to `papers.json.briefings[0]`, and verifies the version. With no briefings, the file keeps every key with null identity fields and empty content. The checker also rejects chunk files the manifest does not list. The catalog grows by adding chunks, so these limits should not need to rise; if one chunk nears its limit, lower `PAPER_CHUNK_SIZE` in `scripts/build.py` together with `PAPER_CHUNK_ENTRIES_LIMIT`.

If another budget must change intentionally, first confirm that payload or image reduction is not practical. Then explain the measured change and rationale in the pull request, and update the checker constant, its contract tests, and this table together. Budget increases require maintainer review; do not raise a limit only to make CI green.

## Writing Good Entries

Please keep entries:
- accurate
- conservative about scope
- concise
- English-only

For `desc`, prefer third-person present tense:
- "Introduces ..."
- "Shows ..."
- "Analyzes ..."

## Before Opening the PR Flow

Please make sure that:
- the resource is either a qualifying paper or a qualifying blog under the rules above
- the generated YAML is valid and complete
- `published_date` is present and uses `YYYY-MM-DD`
